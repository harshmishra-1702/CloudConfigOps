# 3. CORE PROBLEM STATEMENT

Modern cloud infrastructure is increasingly managed through Infrastructure as Code (IaC) tools such as Terraform. However, after deployment, cloud resources may be modified manually through the AWS Management Console, AWS CLI, scripts, emergency operational changes, or unauthorized actions.

These modifications can cause the actual AWS infrastructure to diverge from the configuration defined in Terraform.

This condition is called **configuration drift**.

Configuration drift can result in:

* security vulnerabilities
* accidental public exposure
* inconsistent environments
* deployment failures
* compliance violations
* unexpected infrastructure behavior
* difficult troubleshooting
* increased operational effort
* prolonged security exposure
* difficulty determining who changed a resource and when

Traditional drift detection mainly focuses on identifying that the desired and actual states are different.

The proposed system, CloudGuard, goes beyond simple drift detection by:

1. Detecting configuration drift
2. Identifying what changed
3. Identifying who changed it where possible
4. Assessing the risk/severity of the change
5. Applying a policy-based response
6. Automatically remediating critical deviations
7. Verifying whether remediation succeeded
8. Recording the complete incident for auditing
9. Measuring detection and recovery performance

---

# 4. ONE-SENTENCE PROJECT DESCRIPTION

**CloudGuard is an AWS-based, risk-aware cloud infrastructure monitoring and automation platform that compares Terraform-defined desired infrastructure with the actual AWS environment, detects configuration drift, attributes changes using AWS audit information, evaluates their security/operational risk, and automatically remediates critical deviations according to predefined policies.**

# 6. IMPORTANT CONCEPT: WHAT IS DRIFT?

Example:

Terraform defines:

```text
Security Group

SSH = allowed only from trusted IP
HTTP = allowed
```

Actual AWS configuration becomes:

```text
Security Group

SSH = 0.0.0.0/0
HTTP = allowed
```

Therefore:

```text
Expected SSH rule != Actual SSH rule
```

CloudGuard reports:

```text
DRIFT DETECTED

Resource:
Security Group

Expected:
SSH restricted to trusted IP

Actual:
SSH open to Internet

Severity:
CRITICAL
```

It can then automatically restore the intended configuration.

# 7. NOVELTY OF THE PROJECT

Do NOT claim that basic configuration drift detection itself is novel.

The novelty is the **combination of multiple capabilities into a risk-aware closed-loop system**.

CloudGuard combines:

```text
Infrastructure Drift Detection
          +
Change Attribution
          +
Risk Scoring
          +
Policy-Based Decision Making
          +
Automated Remediation
          +
Remediation Verification
          +
Audit Trail
          +
Performance Measurement
```

Instead of simply saying:

> "The infrastructure has changed."

CloudGuard attempts to answer:

```text
WHAT changed?
WHO changed it?
WHEN did it change?
HOW dangerous is it?
SHOULD it be automatically fixed?
HOW should it be fixed?
DID the fix actually work?
HOW LONG did recovery take?
```

This is the primary research/novelty angle.

The project should eventually investigate questions such as:

### RQ1

How effectively can automated drift detection identify deviations from Infrastructure-as-Code-defined desired state compared with manual monitoring?

### RQ3

Can automated remediation reduce Mean Time to Recovery (MTTR) compared with manual remediation?

# 10. AWS SERVICES AND THEIR EXACT PURPOSE

The following services are planned.

## 10.1 AWS IAM — Identity and Access Management

Purpose:

* authentication/authorization
* roles
* policies
* least-privilege permissions

IAM will control what CloudGuard components can access.

For example, the drift detection Lambda should NOT receive unrestricted AdministratorAccess.

Instead:

```text
Drift Detector Role

Can:
- read required AWS configuration

Cannot:
- perform unnecessary administrative actions
```

A separate remediation role may have only the permissions required to fix supported drift types.

IAM is an important part of the project's cloud security component.

# 15. RISK ENGINE

The risk engine is a major project component.

It should not simply classify everything as "drift."

It should calculate a risk score.

Potential factors:

```text
Resource Criticality
+
Security Impact
+
Public Exposure
+
Environment
+
Type of Change
+
Authorization Context
```

Example scoring:

```text
0–30    LOW
31–60   MEDIUM
61–80   HIGH
81–100  CRITICAL
```

This scoring system is a proposed design and should be refined through research/testing rather than treated as an industry-standard formula.

---

# 16. POLICY-BASED REMEDIATION

CloudGuard should NOT automatically fix every change.

Example policy:

```text
LOW
→ Log

MEDIUM
→ Log + Notify

HIGH
→ Notify + approval/manual remediation

CRITICAL
→ Automatic remediation
```

The exact thresholds and actions should be configurable.

This is important because automatic infrastructure modification can itself be dangerous.

---

# 17. CLOSED-LOOP REMEDIATION

The system should not stop after making a change.

It should:

```text
Detect
 ↓
Remediate
 ↓
Verify
```

Example:

```text
Expected:
SSH restricted

Actual:
SSH public

Remediation:
Remove public SSH rule

Verification:
Query AWS again

Result:
SSH restricted

Status:
RESOLVED
```

This makes the system a **closed-loop automation system**.

Time between actual configuration change and drift detection.

```text
Detection Time =
Detection Timestamp - Change Timestamp
```

## Remediation Time

Time between drift detection and successful correction.

```text
Remediation Time =
Resolution Timestamp - Detection Timestamp
```

---

## MTTR

Mean Time To Recovery.

Average time required to restore infrastructure after drift.

---

## Remediation Success Rate

```text
Successful Remediations
----------------------- × 100
Total Remediation Attempts
```

---

## False Positive Rate

Measure how often the system incorrectly identifies a legitimate configuration as drift.
